## 三、踩坑与网络事实（写入 N-016）

| 坑 | 现象 | 处置 |
|---|---|---|
| `archive.ubuntu.com` 不通 | apt update 超时 / 500 | 换镜像源 |
| 阿里云镜像慢且会断 | 下载 ~110 包用时 17 分钟，偶发 `Connection failed` | 仅用于引导 ca-certificates |
| 腾讯云镜像 302 跳 HTTPS | 基础镜像无 ca-certificates → `Unable to locate package` | **两步法**：先用阿里云 HTTP 装 ca-certificates，再切腾讯云 HTTPS 装其余包 |

**教训**：容器里没有宿主机的 pip/npm 全局配置，镜像源必须写进 Dockerfile / `.npmrc`。

## 九、实测踩到的 6 个坑（已修，写进项目说明书排障表）

1. **内层 containerd overlayfs 解压 Debian 层失败**（`failed to convert whiteout … operation not permitted`）→ daemon.json 关掉 `containerd-snapshotter`，退回经典 overlay2。
2. **内层没有镜像加速**（外层 Docker Desktop 配置不继承）→ daemon.json 配 `registry-mirrors`。
3. **给分区表建外键导致初始化脚本中断**（`alert_records.change_id → item_changes(id)`）→ 去掉该外键；结果：`alert_records`/`audit_logs` 与全部月分区都没建，必须重建数据卷才发现。
4. **`ensure_month_partitions` 参数类型不匹配**（`CURRENT_DATE - INTERVAL` 是 timestamp）→ 显式 `::date`。
5. **容器内 `npm ci` 必超时**（双层 NAT，npm 镜像单请求 25–30s）→ 前端镜像改在宿主机构建，`docker save` + `docker load` 灌进服务器。
6. **`admin@shopbench.local` 登录被拒**（email-validator 把 `.local` 当保留域名）→ 改 `admin@shopbench.cn`，并同步库中账号。

**教训**：`compileall` 过、`compose config` 过，都不等于能跑。**必须真起容器、真调接口**——上面 6 个里有 4 个只有运行时才暴露。

## 十一、BLOCK-2.5 向量检索（2026-11-10）

用户拍板：**模型放本地跑，服务器只做检索**——"服务器需求大的话再扩服务器"。
但仍严格遵 D-003「本机只出不进」：本机是**纯客户端**，主动轮询平台取活、算完写回，不监听端口。

### 交付

| 件 | 内容 |
|---|---|
| schema | `embedding vector(1024)` + HNSW 索引（余弦）+ `search_text` 关键词索引（pg_trgm）+ 统一队列表 `embedding_jobs`（snapshot/query 两种活） |
| ORM | 装 `pgvector`，`Text` → `Vector(1024)`（**修掉"读不了向量"的坑**） |
| 检索 | 向量 + 关键词 + 结构过滤，两路 top-K 用 **RRF** 融合 |
| 接口 | `POST /search`、`GET/POST /embedding-jobs/*`、`POST /snapshots`（灌入即入队） |
| 算力节点 | `compute-node/worker.py`（本机）、`scripts/start-compute-node.ps1` |
| 模型 | Qwen3-Embedding（千问）→ `E:\01-model\M-028-Qwen3-Embedding-*@v1`（Z-02 一模型一夹） |
| 验收 | `scripts/verify_vector_search.sh` |

### 三个实测硬事实（已写成 N-017）

1. **pgvector 的 HNSW/IVFFlat 索引最多 2000 维**——Qwen3-Embedding-4B 原始 2560 维**建不了索引**
   （报错 `column cannot have more than 2000 dimensions for hnsw index`）。
   → 这直接推翻"模型越大越好"：维度是服务器内存的直接成本。
2. **Matryoshka（MRL）模型可自己降维**：Qwen3-Embedding 系列官方支持截断后重新归一化
   → 4B 截断到 1024 维；0.6B 本身就是 1024 维（无需截断，schema 也不用改）。
3. **Python 侧必须装 pgvector 适配器**，否则 ORM 只能把 vector 列当 Text，读的时候解码失败。

### 降级（K2 的落地）

算力节点不在线 → 检索**自动降级为纯关键词**并在响应里标明 `degraded=true`，不卡死用户。已实测通过。

### 网络坑

本机到 HF 单连接只有 ~0.6 MB/s，8GB 的模型下到一半被掐断且**镜像不支持断点续传**（重试会清零重来）。
→ 自写 `compute-node/tools/parallel_fetch.sh`：**多连接分段 + Range + 分段重试**，实测可用。

### 顺带修的

- 所有 `.ps1` 加 UTF-8 BOM（Windows PowerShell 5.1 把无 BOM 的 UTF-8 当 ANSI 读，中文会把语法读崩）；
- 验收脚本加 `PYTHONIOENCODING=utf-8`（Windows 的 python 默认 GBK 输出，中文 JSON 会写坏）。

## 十二、一个值得记住的教训：分片下载必须核 sha256

**现象**：并行分段下载，合并后文件**大小居然吻合**（但其实是错的），
直到用官方 sha256 校验才发现——本地比官方大了 107MB。

**原因**：分片下载改了并发数（8 → 10 → 12），块大小变了；
脚本的"跳过已完成段"逻辑只按**文件名**判断，旧轮次的小尺寸分片被当作"已完成"跳过，
拼接时又把新旧两套分片一起 `cat` 进去了。

**教训**：
1. 分片名必须带**块大小**（`part_00_${CHUNK}`），换并发数才不会串段；
2. 拼接只拼**本轮**的分片；
3. **大小一致 ≠ 内容正确**，下载完必须核官方 sha256（HF API 的 `lfs.oid`）；
4. 验收要"真验"——看文件在不在、大小对不对都不算数。

**已落地**：`parallel_fetch.sh` 改为按块大小命名 + 只拼本轮 + 支持 `EXPECT_SHA256` 校验；
新增 `compute-node/tools/verify_model.py` 独立校验脚本（含 HF 官方值自动拉取）。
