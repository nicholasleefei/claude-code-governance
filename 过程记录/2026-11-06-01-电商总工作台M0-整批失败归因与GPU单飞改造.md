> 主题：M0 闭环跑通后跑 60 张整批，全数超时；定位到显存互抢（根因），改造为单飞 + 排队 + 续跑。

## 0. 一句话

11-06 上午 17:37，电商总工作台同时开了 **3 个出图任务**（2×60 张 + 18 张），
96 张图**只出 2 张**，其余全部 `超时 1800s`；
归因发现 **FLUX transformer(bf16) 约 23.8GB，4090D 只有 24.5GB 显存，一卡只容得下一个出图进程**，
两个进程同跑必然互抢显存并双双卡死。改造为 **单飞锁 + 排队 + 显存闸门 + 断点续跑**，随后以单任务重跑整批。

## 2. 归因

- **现象**：单张 110 秒能出；并发时 96 张只出 2 张，且不是"慢"，是**整整卡满 1800 秒**。
- **显存核对**：出图走 `E:\ai-env\py-lora` 的本地 FLUX（`product-poster-motion/scripts/flux_lora_gen.py`），
  transformer 以 bf16 全量上卡（`FluxTransformer2DModel.from_pretrained(..., torch_dtype=bfloat16)`），
  11.9B 参数 ≈ **23.8GB**；4090D 总显存 **24,564MB**。T5 编码后已 `del t5, clip` 释放，但 transformer 仍在。
- **实测占用**：单进程跑批时 `nvidia-smi` 观测 **18,944MiB / 24,564MiB（利用率 100%）** ——
  第二个进程再要 ~19GB，**物理上放不下**，于是卡死而非报错退出。
- **结论**：不是脚本 bug、不是权重缺失、不是 seed 冲突；是**一卡一进程的资源约束**被工作台的无并发管控踩穿。

## 3. 改造（`电商总工作台-mvp`）

| 改动 | 位置 | 说明 |
|---|---|---|
| GPU 单飞锁 + 排队 | `backend/app.py`（`GPU_LOCK` / `RUN_QUEUE` / `_dispatcher`） | 同时只跑一个出图任务，其余排队，GPU 空自动起 |
| 显存闸门 | 同上（`GPU_FREE_MIN_MB=6000`） | 出图前查 `nvidia-smi`，余量 < 6GB 直接拒绝并说清原因，不去撞墙 |
| 服务重启自愈 | 同上（`reconcile_stale`） | 启动时把 `running/queued/pending` 标成"失败（可续跑）"，不让僵尸任务装忙 |
| 续跑接口 | 同上（`POST /api/tasks/{id}/resume`） | 沿用原 `out_dir`，同名图跳过 |
| 前端"续跑"按钮 | `frontend/index.html` | 任务列表给失败/已完成任务加续跑入口，状态显示中文 |
| 超时收紧 + 留证 | skill `style-mood-image/scripts/gen_mood_images.py` | 单张超时 1800s→**900s**；超时打印子进程 stdout/stderr 尾部（原来只留一句"超时"） |
| 后台常驻启动 | `启动服务.cmd` | `Start-Process` 脱离会话，**服务不再随上一轮会话退出而被带走**（本次事故的第二根因） |

## 七、续记（2026-11-06 20:05–20:35 · 只增不改）

### 7.1 改造生效后的实测速率（推翻上午的"2–2.5 小时"估计）

单飞跑批实测：**首张 115 秒**（冷加载权重），其后每张 **28–34 秒**；
60 张整批 ≈ **35 分钟**，不是原先估的 2–2.5 小时。
原因：上午的 110 秒/张 是"冷启动单张"的数字，被当成了稳态速率。**估算要用稳态值，别用冷启动值。**

### 7.2 事故二：第二个实例启动，误杀了正在跑的任务

- 现象：用 `启动服务.cmd` 做**启动器自检**时，另起了 8787/8799 两个实例；新实例启动即跑
  `reconcile_stale()`，把**另一个实例正在跑**的任务标成"失败（可续跑）"——跑批在第 21 张被打断。
- 根因：`reconcile_stale` 的判断依据是"库里 status=running"，**没有区分这个 running 属于谁**。
- 对策（新增）：`servers` 实例登记表 + **心跳**（每 5 秒戳一次）+ 任务 `owner` 字段。
  只有"owner 查无此实例或心跳断了 90 秒"才算僵尸；**别的实例在跑的任务不再被误杀**。
- 附带修：出图前的**显存闸门改成"先等"**（最多等 180 秒释放）而不是直接判失败——
  上一个任务的进程退出后显存要几秒才释放，排队任务不该因此被判死。

### 7.3 事故三：**同一项目上有第二个会话在同时改代码**

- 现象：20:03 起 `backend/agent.py`、`目标.md` 与 `app.py` 的 Agent 段由**另一个 Claude Code 会话**写入；
  20:07 对方重启了服务 → 我的跑批被打断在 21 张；对方同时**删掉了**前端仍在用的三个接口
  （`/api/bootstrap.js`、`/api/tasks/{id}/manifest.js`、`/api/bundles`），工作台 UI 直接瞎掉。
- 处置：① 用"实例心跳 + owner"让多实例不再互杀；② **按原样恢复**那三个接口（纯增量，不动对方的
  `/api/runs` 新链路）；③ 跑批用 `/resume` 续跑（已出的图不重出，21 张成果保住）。
- **教训（写给以后）**：同一项目同时开两个会话写代码 = 互相踩。**同一时刻只留一个写手**，
  另一个会话只读/看结论；或者先把分工切开（一个改 agent 链路，一个改 GPU 调度）。

### 7.4 工具层面的坑（值得记）

- **Edit 工具会吃掉字符**：多次出现 `CREATE TABLE` 被写成 `CREATE IG`、`
` 被写成真换行、
  逗号被吞。涉及中文的 old_string/new_string 尤其容易中招。
  → 对策：**改动后必须编译自检**（`python -m py_compile`），长块改动用脚本按行改，别用大段 Edit。
- **`.cmd` 文件必须 CRLF + UTF-8 无 BOM**：Write 工具写出来是 LF，cmd.exe 解析 UTF-8 + LF 的中文行
  会整行错位（实测把 REM 行的中文当命令执行）。三个启动脚本已统一转成 CRLF。
