E-01Z-01 适用范围 · 怎么落地◂ 返回总则
落地说明

这条是效力条款兼部署条款——它本身规定「这套总则管到哪儿」，所以它的落地说明就是部署方案。

怎么做到全机生效：获准后由总则书记把本条条文镜像到用户级文件 C:\Users\pc\.claude\CLAUDE.md。该文件在本机每次会话、任意目录启动时自动全文加载，因此总则一到那里，就等于对全机所有会话生效。今后每新批一条，都沿同一条通道追加镜像（软规则）或写入 settings.json（红线）。总则.html 是唯一权威人读稿，全局文件只是它的执行副本——只由会议侧单向写入、不手改，防止两处跑偏。

效力边界＝配置可被读取的边界：本机 CLI／桌面端会话读取本机用户级配置 → 在适用内；claude.ai 网页端运行在云端、读不到本机配置 → 够不着、不在适用内；换一台电脑或换一个账号需各自部署；若将来本机接入企业托管策略层，个人配置让位于托管策略。

优先级（冲突时谁说了算，自高而低）：当次会话用户的临时指令 ＞ 红线条款（系统层 deny，不因项目豁免）＞ 项目级规则（在具体项目里可覆盖总则软规则）＞ 总则软规则（默认基线）。

校验：任选一个与本文无关的文件夹新开会话，用 /context 查看是否已加载到该全局文件；/status 查看设置来源。

通俗解释
把总则比作公司《员工手册》。它不塞进每个人的抽屉，而是贴在公司门口告示栏（用户级配置）——不管你在哪个办公室（哪个项目文件夹）上班，进门都得先看到，所以全公司都适用。范围就到这块告示栏能被人看到的地方为止：别的城市的兄弟公司（别的电脑）看不到、临时在云端远程办公的人（网页端）也看不到，那就管不着。手册还写清了规矩的优先级：你当场说的话最管用 → 绝对红线（谁也不许破）→ 各办公室自己的补充规定 → 手册里的通用条款（兜底）。
名词解释

  • claude.ai 网页端Claude 的云端网页版聊天，运行在云端服务器，读不到你这台电脑上的配置文件。

E-02Z-02 模型文件统一仓 · 怎么落地◂ 返回总则
落地说明

这条属于「文件与存储」的软规则约定——它不拦危险动作，而是规定 Claude 在本机任意项目里处理模型文件时的默认落点与登记方式，目标是杜绝重复下载、误入版本库、散落各处。

落点约定：Claude 下载或保存模型时，默认写 E:\model\，不落入项目目录；需要某模型时先查 E:\model\ 根目录的 index.html 台账（或扫描各夹）是否已有，已有则直接以绝对路径引用、不重复下载。

结构与命名：一模型一夹；夹名＝编号-模型名@版本（编号由台账顺延分配，只增不重、删除不回收，避免旧引用错位）。每夹内 index.html＝该模型说明书（名称／来源／参数规模／格式／许可／校验和／加载示例），供人工查找与记录。E:\model 根目录 index.html＝总台账（编号登记与查找入口）。

工具缓存：Hugging Face、Ollama、LM Studio 等工具自行下载时，缓存是哈希散装结构，无法强行拆成一模型一夹；通过环境变量把缓存根指到 E:\model\_cache\<工具>\ 物理归拢即可（如 HF_HOME、OLLAMA_MODELS、XDG_CACHE_HOME；属系统级变更，另行清单批准后生效，本机默认值见待批清单）。

例外与兜底：项目内联调必需的小模型可暂放 <项目>\models\，但须在台账登记、并用 .gitignore 排除（防误入版本库）；定期巡检项目与用户目录，凡发现 E:\model 之外的大体量模型文件（.safetensors／.gguf／.bin 等）即「漏网」，一律归拢或登记。

边界：仅约束本机（E 盘为本机专用约定，随 Z-01 范围生效）；不约束云服务托管的模型。

通俗解释
把模型想成工具箱里的电钻：不再每个工地（项目）各买一把（各下载一份），而是全公司统一放一个工具间（E:\model），每把钻有编号和登记牌（编号＋index.html）——要用就去工具间借（先查台账，有就复用），买新的按编号入库。工具自己下载的散件（HF/Ollama 缓存）虽然拆不成一箱一箱，也统一堆进工具间的杂物仓（_cache），免得散落工地。哪个工地临时非要在现场放一把小工具（项目内小模型），可以，但要在登记本记一笔、并保证不会混进资料袋被带走（.gitignore）。隔段时间巡一遍所有工地，凡发现落单的钻（不在 E:\model 里的大模型文件），就归库或登记。
名词解释
  • 模型文件 / 权重训练好的 AI 模型本体，常为数百 MB～数十 GB 的大文件（.safetensors/.gguf/.bin/.pt 等）。
  • 落点程序把下载或保存内容写进磁盘的具体路径。
  • E:\model\本规则约定的全机模型统一仓（根目录）。
  • 一模型一夹每个模型独占一个独立文件夹的整理方式。
  • 台账 / index.html登记与查找用的清单文件；E:\model\index.html 是总台账，每模型夹内另有该模型的说明书页。
  • 编号给每个模型分配的稳定序号（M-001…），用于查找定位；只增不重、删除不回收。
  • 绝对路径从盘符写起的完整路径（如 E:\model\M-001\…），与"当前目录在哪"无关，任意项目都能引用。
  • 工具缓存 / 缓存软件把下载内容暂存以待复用的目录；HF/Ollama 等工具的缓存为哈希散装结构，布局由工具自己管理。
  • Hugging Face最大的开源模型托管平台；下载缓存可用 HF_HOME 重定向。
  • Ollama本地运行大模型的常用工具；模型目录可由 OLLAMA_MODELS 指定。
  • LM Studio本地图形化运行模型的工具。
  • 环境变量操作系统级的全局设置项，程序启动时读取；如 HF_HOME、OLLAMA_MODELS、XDG_CACHE_HOME。
  • XDG_CACHE_HOME一个通用缓存根环境变量，很多工具会兜底读取。
  • .gitignore版本库忽略清单；列出的路径不会被 git 提交。
  • 版本库 / git代码版本管理工具；模型大文件应避免进入其中。
  • 校验和对文件内容算出的指纹，用于核对下载文件是否完整、未损坏。
  • 巡检定期扫描、把 E:\model 之外的大体量模型文件归拢或登记，治"遗漏"。
E-03Z-03 技能台账 · 怎么落地◂ 返回总则
落地说明

这条属于「文件与存储」的登记制软规则：与 Z-02 模型仓「把实体统一搬进 E:\model」相反，skill 是实体不动、只做登记。

实体不强搬不强拆：skill 不强搬、不拆散、不做目录联接，各自待在标准生效位置原样运行——用户级 ~/.claude/skills、项目级 .claude/skills、插件内自带目录。一个 skill 能否被 Claude Code 识别，取决于它是否待在会去扫描的固定位置；搬走、或为了「入库」复制一份到台账，反而会让它失效。因此 E:\skill\index.html 只是台账登记处、不是实体仓。

台账字段：每条记 S 编号／名称／类型（外部下载部署｜自写沉淀）／安装或沉淀日期／位置（完整路径，并注明所属 用户级/项目级/插件）／能力一句话／来源／状态（在编｜停用（可删）｜待测）／备注。编号 S-001 起顺延分配、只增不复用；与 Z-02 的模型 M 号相互独立、各排各的。

登记口径：外部下载部署的记来源（仓库／作者）与安装日期；自写沉淀的记「自写沉淀 · 日期」。某 skill 究竟能干什么，以它所在目录原生的 SKILL.md 为准——台账只作一行索引、不另抄能力全文，避免两处说法漂移。

停用与删除：停用不删夹，只把状态改为「停用（可删）」；删除前先翻台账「位置」列确认影响面。尤其工具托管类 skill（如 @tts-open-toolkit/cli 托管的 tts-* 系列，本体由该工具统一管理），应走该工具 CLI 的管理命令卸载／升级，勿手工删目录——否则工具下次运行可能按清单补回、或留下指向已删实体的坏引用。

巡检补登记：定期扫描 ~/.claude/skills 等标准生效位置，凡发现未登记的 skill（新装或漏记）即按上述字段补记；反向核对台账里「实体已不在」的条目，把状态改为「停用（可删）」。

通俗解释
Z-02 收模型，是把实物统一搬进大仓库（E:\model），一台一格、编号上架。skill 不一样——它更像一台台各有专用电源插座的家电：洗衣机必须插在阳台那个专用插座上才转得起来，你不能嫌它占地就把它硬搬到楼道里，也不能剪了插头重新接线。所以这条的规矩是：电器原样待在各自该待的插座上（用户级 / 项目级 / 插件三个标准位置），不搬不拆；只在小区门口物业台放一本登记本（E:\skill 台账），记「几号楼几户装了台洗衣机、何时装的、干什么用、哪买的、出问题找谁」。想找某个技能，翻登记本就知道它在哪个插座上、怎么用；想拆、想升级，也先翻登记本看它接的什么线——尤其那种整栋楼统一供水供电的（工具托管类），要让物业按规程断电（走工具 CLI 的管理命令），别自己上手剪管子。
名词解释
  • skill（技能）Claude Code 的可复用能力包：一个目录，内含 SKILL.md 说明与可选资源，放进标准位置后被 Claude 按需加载。
  • SKILL.mdskill 目录内的说明文件，是「这个技能干什么、怎么用」的权威定义，Claude 据此决定何时调用。
  • user-invocableSKILL.md 里的可选设置；标了它，用户可手动点名调用该技能（如 /技能名），而不只靠 Claude 自主触发。
  • 目录文件夹。skill 以一个目录为单位存在，目录里装着说明与所需文件。
  • 路径定位文件位置的一串地址：绝对路径从盘符写起（如 C:\Users\pc\.claude\skills\…），与当前在哪无关；相对路径从当前所在目录算起。
  • 用户级 ~/.claude/skills全机、本账号通用的技能目录（~＝用户主目录 C:\Users\pc）；装在这里任何项目都能用。
  • 项目级 .claude/skills项目文件夹内的技能目录，只在该项目里生效、随项目走。
  • 插件（plugin）扩展包分发形态，可自带 skills；其技能由插件目录托管，也是「标准生效位置」之一。
  • index.html目录的清单／说明网页；E:\skill\index.html 是技能台账总页（Z-02 的 E:\model 也用同名文件作台账）。
  • 台账只作「登记、索引、查找」用的清单，不存实体——与「实体仓」相对。
  • 编号（S 号）技能在台账里的稳定序号 S-001…，顺延分配、只增不复用；与 Z-02 的 M 号是两套独立编号。
  • 工具托管类 skill由某工具／CLI 统一安装、升级、卸载的技能（如 @tts-open-toolkit/cli 托管的 tts-* 系列），须走其管理命令、勿手工删。
  • CLI命令行界面（Command-Line Interface）；工具托管类技能的增删改靠敲管理命令完成。
  • 镜像部署 / 镜像文件把权威内容复制／同步成一份执行副本；此处强调对比——skill 不做镜像式实体仓，只登记。
  • 标准生效位置Claude Code 会去扫描并识别技能的几个固定目录：用户级、项目级、插件目录。
  • 外部下载 vs 自写沉淀台账「类型」字段两态：前者从网上仓库／作者处安装来，记来源与安装日期；后者自己写好放进去的，记「自写沉淀 · 日期」。
  • 巡检定期扫描标准位置：把漏登记的技能补记、把实体已消失的条目改状态，治「漏」。
  • 停用（可删）台账「状态」之一：不再用但不立即删，保留实体与登记；确认无影响后再真正删除。
  • E:\skill 与 E:\model 分工E:\model 收模型实体（实体仓）；E:\skill 只收技能台账（登记制）。两者存储策略相反。
E-04Z-04 MCP 与 CLI 工具台账 · 怎么落地◂ 返回总则
落地说明

这条属「配置与运行环境」的登记制软规则：与 Z-03 技能台账同属「实体不动、只做登记」一族，但登记对象扩到两类外部接线——MCP 服务器与CLI 工具。它不像 Z-02 模型仓那样把实体搬进统一目录，也不对工具做复制或目录联接，一律让它们在各自生效位置原样运行。

为什么只能登记、不能搬：MCP 不是一个可拷走的文件，而是一段「注册进 Claude Code 的配置＋一条启动命令」。它注册在 Claude Code 配置里——项目级 .mcp.json、用户级 ~/.claude.json（其内 mcpServers 段）；是否被识别，取决于「注册位置＋传输方式」是否成立，一旦从注册处挪走即断连。CLI 工具本体由包管理器/安装器放进 PATH 或已知路径，擅自搬动会破坏依赖与系统识别。故本条不搬文件、不做目录联接。

两本平行总台账：E:\mcp\index.html 与 E:\cli\index.html 各为一本总台账（纯登记处、非实体仓），MCP 与 CLI 各排各号、互不混编：MCP-001… 与 CLI-001…，顺延分配、只增不复用（沿用 Z-02/Z-03 的编号纪律：删除不回收号，防旧引用错位）。

登记字段（一行一条）：名称／能力一句话／来源／添加日期／位置或注册 scope（注明项目级 vs 用户级，项目级写明承载的 .mcp.json 所在项目）／启动命令／状态（在编｜停用｜待测）。凭据纪律：含密钥或远程项一律只记「所需环境变量名」（即运行时去读哪个变量的名字，如 OPENAI_API_KEY 这类名称本身），明文 key/口令绝不写入台账——把台账的泄密面压到最小。

卸载与测试走官方通道：增删改查 MCP 注册一律用 Claude Code 自带命令 claude mcp remove／claude mcp list 等，勿手工编辑配置段或删目录；CLI 本体的升级/卸载走其来源包管理器（npm/pip 等）。

npx/uvx 与工具托管：由 npx／uvx 即拉即跑、或由某工具自动托管者（如 @tts-open-toolkit/cli 拉起的 tts-*），本体由包源/工具统一管理，台账只登记启动命令、不搬实体；其运行缓存的物理收拢属系统级变更，另行批准后执行（呼应 Z-02 缓存归拢思路）。

生命周期同步：新增／删除／停用任一 MCP 或 CLI 后即更新对应台账；定期反向核对「实体已不在」的条目、把状态改为停用，与 Z-03 的巡检口径一致。

跨 skill/MCP/CLI 互链：同一来源横跨多本台账的工具，只在一处正式登记、其它处写编号互链指过去、不重复登记。例：tts-open-toolkit 已按 Z-03 在技能台账 S-004 立户，则其 CLI 侧在 E:\cli\index.html 只标「本体由 tts-open-toolkit 托管，见 S-004」，不再单开一条重复登记。

通俗解释
Z-02 收的模型是整箱整箱采购的货，能统一搬进大仓库、一格一箱上架；MCP 和 CLI 却更像是已经接进大楼里的水电管网接口——想给 Claude 接一个「查天气」的服务，你得在楼里的接口面板上接好线（在配置里注册），告诉它这一路是干什么的、走哪根管道（stdio/HTTP）、由谁合闸启动。这时候要是硬把接口「搬进仓库」，等于把插头从面板上拔下来——大楼立刻就不认这一路了。所以对它们只能记、不能搬：在物业登记本（E:\mcp／E:\cli 台账）上写「几号楼哪个面板接了哪个服务、由谁启动、接的什么电」。带钥匙/密令的服务，登记本只记「这路电接的是哪块电表」（要哪个环境变量名），绝不把钥匙抄在登记本上。想看看现在接了几路，翻登记本或直接问中控（claude mcp list）；要拆掉一路，按规程断电（claude mcp remove），别硬拔。有些设备随叫随到、本体还在供应商那儿（npx／uvx 拉起的），登记本上照记「按哪个按钮能叫它」就行。同一套设备既当技能又当 CLI（如 tts-open-toolkit），只在技能那本上正式立户，CLI 这本标一句「见 S-004」，不重复立户。
名词解释
  • MCP模型上下文协议（Model Context Protocol）：一套统一接口标准，让 Claude Code 通过「注册好的服务器」去调用外部数据源与工具。
  • MCP 服务器实现 MCP 协议、向 Claude 提供能力的一端进程/程序；运行在本地（stdio）或远端（HTTP），注册后才可被调用。
  • stdio / HTTP 传输MCP 客户端与服务器之间的两条「管道」：stdio 走本地进程的标准输入输出（本机工具用），HTTP 走网络（远程服务用）。
  • 注册 / server 注册在 Claude Code 配置中登记一条 MCP server（名字、启动命令、传输方式）；注册了才被识别，未注册的服务器对 Claude 而言不存在。
  • config / scope（项目级 vs 用户级）配置文件及其生效范围：项目级写进项目里的 .mcp.json，只在该项目生效；用户级写进 ~/.claude.json，对本机所有会话生效。
  • .mcp.json项目级 MCP 配置文件，放项目根目录，声明该项目要接哪些 MCP server，随项目走。
  • ~/.claude.json用户级 Claude Code 主配置文件（~＝C:\Users\pc），可含全局 mcpServers 段，供本机各会话共用。
  • PATH操作系统查找可执行文件的路径清单；一个 CLI 工具能被直接敲名字运行，前提是其所在目录在 PATH 里（或用绝对路径/管理器调用）。
  • CLI命令行工具（Command-Line Interface）；本条登记对象之一，凡以终端命令调用的工具都算。
  • npx / uvxNode 与 Python 生态的「即拉即跑」运行器：npx 跑 npm 包、uvx 跑 Python 包，按命令临时拉取执行、本体由包源托管，故台账只记启动命令、不搬实体。
  • 托管实体的安装、升级、卸载统一交由某工具/包管理器负责，不手工管理；被托管的工具（如 tts-open-toolkit 拉起的 tts-* 系列）只登记、不搬。
  • 环境变量名 vs 明文凭据台账只记「凭据由哪个环境变量提供」的名字，绝不写入 key 本身的明文——把台账泄密面压到最小。
  • index.html 台账登记与查找用的清单页；E:\mcp\index.html、E:\cli\index.html 各为 MCP、CLI 的总台账，与 Z-02/Z-03 同款约定（非实体仓）。
  • 编号只增不复用MCP-001… / CLI-001… 顺延分配、删除不回收号；保证每条记录可追溯、旧引用不错位。
  • 跨表互链同源工具横跨 skill/MCP/CLI 多本台账时，只在一处正式登记，其它处写「→ 某编号」指过去，避免重复登记与口径漂移。
  • claude mcp list / claude mcp removeClaude Code 内置的 MCP 管理命令：list 查看当前已注册的服务器，remove 移除某条注册；卸载/核对 MCP 一律走这里，勿手工删。
  • 镜像把权威内容复制/同步成一份执行副本的做法；本条要点在对照——MCP/CLI 与 skill 一样不做镜像式实体仓，只登记、原样引用。

落地说明

这条把「多 Agent 协作」从纯方法论提升为全机行为默认（呼应 Z-01 适用范围：本机全部 Claude Code 项目通用）。它自身不含拆法细则——何时拆 / 拆几个 / 怎么排的细则在 会议章程 P-9（规范底稿）与「多 Agent 协作」Skill（用户级 ~/.claude/skills\multi-agent-collab\，已登记 E:\skill 台账 S-009），本则正文只立触发默认。

触发时机：当收到大体量、可拆分的指令，或用户表达"看看是否需要多 Agent 协作"等类似意思时，默认按多 Agent 流程评估并执行，而非默认单线程硬扛。评估用 P-9「三问」：① 够大？② 切得出相互独立、可并行的子块？③ 结果能验收？三问全中才拆；需与用户反复对齐、小活、强耦合 → 不拆、走单线程。

边界纪律：顶层主会话始终在对话中、常驻不中断；派出的智能体只是主会话「可随时调整的延伸」，不是对话交接对象。任何拆分不以让用户等待或主会话下线为代价。主会话同一时刻只回一件事（单线程）；并行只压缩墙钟时间、不增加对话带宽。拍板权在用户、防越权；智能体完成＝「事件报上来」＝进度，不等于批准。

怎么排（通用编排原则）：执行数＝独立子块数（常规 2–5）；结果关键/不可逆/高风险 → ＋1 对抗性核验；需留痕 → ＋1 纪要；指挥者（小希型）不计入工人数；单批总数建议 ≤6，超则分批。各子块互不依赖 → 一批并行；有先后因果 → 流水线（段内再并行）。只读（Explore）/ 规划（Plan）/ 执行（工人）/ 核验（复看）分开；简报自足、各管各、互不覆盖、只回结论。项目家族参考模板 F1–F6（调研/数据/创作/工程/产品/仿真）仅供按重心参考，非强制归类、具体项目可不参考。

本治理体系的实例：批量落文件即按 P-8 由 书记长 领衔、编排 ≥3 书记子 Agent 并行（草总执三页各管一页、总则书记同轮镜像）；普通会话需拆活时，亦按上述原则先只读并行摸底再定人数派活。触发与执行细则见 Skill 本体。

通俗解释
把顶层主会话想成一直在灶台前掌勺的大厨：大厨不会把厨房交给别人就离场，而是人一直在灶前。切菜、备料这些能分开的活，分给几个帮厨同时干——他们各自干完端一盘过来，大厨边掌勺边收；有先后的（先蒸再炒）就排好顺序一道道上；要上大席的菜，末尾再请一位老饕先试味挑刺（对抗性核验）。什么时候才值得分活？菜够大、能切成互不牵连的几份、每份做完能验收，三样齐全才分；只是随口要个小菜、或口味还得反复跟客人确认的，就自己一锅炒。帮手再多也只省出菜时间，不替大厨跟客人说话——最终拍板、加人减人、换菜式，永远是客人（用户）一句话的事。
名词解释
  • 多 Agent 协作把一个任务拆给多个智能体并行或流水线协作完成的做法；本机在收到大体量/可拆分指令时默认按此流程评估执行。
  • 顶层主会话用户对话中的「我」；常驻、对话不中断，派出智能体后仍在对话中、可随时调整，是唯一与用户对话的对象。
  • 子智能体 / 书记主会话派出的执行单元；书记是治理体系内专责执笔页面（草案/总则/执行结构）的子 Agent 称谓。
  • 何时拆三问①够大？②能否切出相互独立、可并行的子块？③结果能否验收？三问全中才拆，缺一即单线程。

  • 对抗性核验末尾派一个专门挑错的智能体复看结果，用于关键/不可逆/高风险任务过质量关。
  • 墙钟时间 vs 对话带宽并行只压缩真实经过的时间（墙钟），不增加同一时刻主会话能对话处理的量（带宽）。
  • 简报自足派给子智能体的任务简报把路径、期望产物、约定与验收清单写全，使其能独立交付、只回结论。
  • 拍板权在用户拆分、增减人、换方向、批准都归用户/主会话即时决定；子智能体不替用户做其权限不允许的动作。
  • F1–F6 参考模板按项目重心分的六类示意排法（调研/数据/创作/工程/产品/仿真）；非强制归类，具体项目可参考、可套用、可不参考。
